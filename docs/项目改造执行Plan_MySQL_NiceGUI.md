## 0. 执行边界与总目标

将现有研究工具升级为单实例、单操作者的异步研究服务，完整展示：

**提交需求 → 后台排队 → 分问题研究 → 检索与证据校验 → 阅读报告与原文 → 历史查询 → 失败后重试。**

必须同时完成两条主线：研究结果可信度、实际业务服务能力。不能仅添加数据库和队列，而保留现有结论支持不足的问题。

执行约束：

- 原计划阶段只编写文档；用户后续已授权修改项目、安装 Docker / WSL 并进行有限真实验证。本文件同时保留原始验收要求和实际进度。
- 已按授权实施 P0–P6；涉及新增付费任务、破坏性数据处理或发布仍单独处理。5 个真实任务名额已全部消耗，不再新增调用。
- 保留 Python、LangGraph、现有模型接入、Tavily、HTTPX、预算控制、资料输入、Markdown 导出、Trace 和 pytest 的有效实现。
- NiceGUI 替代 Streamlit；MySQL 成为唯一正式业务数据库。SQLite 只保留必要的旧数据读取/迁移功能，不维护两套完整后端。
- 不加入 PostgreSQL/pgvector、独立向量数据库、Kafka、Kubernetes、多 Agent 投票、微服务、复杂账号权限或公网生产运维。
- 首版提供任务持久化、状态查询、取消与失败重试；不承诺 LangGraph 任意节点断点续跑，不把状态快照称作 checkpointer。
- 不增加依赖只为扩充简历；不以节点数、测试数量或依赖数量作为完成标准。
- 既有个人 QA 文档、简历、学习材料、真实运行记录、未跟踪文件及本地凭据保持原状。
- 不自动提交或推送 GitHub；本计划批准实施与批准发布分开理解。

## 1. 最终技术清单与职责

| 技术 | 本次必须承担的职责 | 不承担的职责 |
|---|---|---|
| Python | 业务逻辑、研究核心、检索、测试 | 不另加第二后端语言 |
| LangGraph | 研究内部状态流转、条件补查、有限修复 | 不承担分布式任务调度 |
| NiceGUI | 研究工作台、进度、报告/证据、历史与评测 | 不在页面回调执行完整研究 |
| FastAPI + Pydantic | HTTP 契约、请求校验、任务接口 | 不在请求中同步跑完整研究 |
| MySQL + SQLAlchemy + Alembic | 业务事实、事务、索引、结构迁移 | 不兼作消息代理或假定自带图恢复能力 |
| Celery + Redis | 后台执行、队列、有限重试 | 不将 Redis/Celery 结果作为任务事实来源 |
| 现有模型 API 适配层 | 规划、结构化生成、语义检查、用量记录 | 不假定聊天接口提供向量能力 |
| Tavily + HTTPX | 搜索与有界抓取 | 不增加另一套浏览器抓取系统 |
| BM25 + Embedding + RRF | 对本次研究的有限语料进行混合检索 | 不建立跨任务向量知识库 |
| Docker Compose | Web、Worker、MySQL、Redis 的可复现环境 | 不承担集群调度 |
| pytest + GitHub Actions | 单元、集成、故障回归与持续检查 | 不用 Mock 证明真实答案准确率 |

Embedding 的具体模型/供应方在 P2 的固定资料实验中确定，记录中文与跨语言效果、资源需求、许可、版本与费用。此处不臆定当前账户具备向量接口权限。下载模型或调用付费接口前按实际环境权限与用户预算执行。

新增依赖版本在 P0 核验兼容性后锁定，不直接填写未经安装验证的版本号；部署镜像不使用浮动 latest。

| `evals/metrics.py` 以流程状态及内部判断为主 | 独立标注不能由运行器自评代替 |

历史记录（不是本轮重新测得）：85 项 pytest 通过；现有 20 条离线任务主要验证行为；同一 SQLite WAL 问题的三次真实运行均未达到 completed。不要把它们写成新系统成绩。

永久保留以下回归场景：

- 两个明确问题分别验收，不能合并成一个含糊问题后判定全部覆盖。
- WAL 官方正文关于读写互不阻塞的句子，不能单独支持“只有一个写入者”和“仍可能 SQLITE_BUSY”两个结论。
- 相关原文在正文后部仍能进入候选；同一段的条件、例外不能被切丢。
- 官方域名下的论坛不自动等同于官方技术文档。
- 搜索摘要、完整正文、用户材料与 Mock 明确区分，降级不伪装成正常研究结果。
- “官方原文：”这类引导语不算独立事实；事实写进标题或限制说明也不能逃过支持检查。

## 3. 目标结构与数据流

```text
浏览器
  │
  ▼
Web 进程：NiceGUI 页面 + FastAPI API
  │                │
  └──── 业务服务层 ─┘ ───── MySQL
             │                ▲
             ▼                │
           Redis → Celery Worker → LangGraph
                                       │
                                       ▼
                             搜索 / 抓取 / 模型 / 检索
```

同一 Web 应用内，页面与 API 调用共享业务服务，不强迫页面绕行本机 HTTP，也不让页面直接读写数据库。CLI 保留为客户端或明确标记的核心调试入口，不偷偷建立 SQLite 第二运行体系。


## 4. 先固定的业务契约

### 4.1 任务与研究质量分开

- `Task` 表示用户一次提交的研究需求；`Attempt` 表示一次具体执行。任务重试产生新 Attempt，不覆盖前一次报告和调用记录。
- 执行状态：`pending_dispatch → queued → running → succeeded / failed / cancelled`；允许 `pending_dispatch`/`queued` 被取消，允许失败原因中标记 worker_lost。
- `cancel_requested` 单独记录，运行中取消为协作式取消；不把“已请求”显示成“已取消”。
- 研究质量：`unassessed / completed / partial / insufficient_evidence / needs_review / demo`；质量与执行状态独立。
- 执行成功只表示流程与结果保存成功；证据不足的报告可以执行成功，但绝不显示为研究完成。
- `completed` 是通过当前质量门槛，不能解释为外部事实绝对正确。

### 4.2 数据模型初版

持久化实体先控制在：`research_tasks`、`task_attempts`、`source_documents`、`evidence_chunks`、`reports`、`execution_events`、`external_calls`。必要时新增评测记录，不提前为假设中的业务拆出大量表。

- 任务：请求与非敏感配置快照、幂等键/请求摘要、当前尝试、时间、版本号。
- 尝试：序号、派发状态、执行状态、质量状态、取消标志、执行令牌、心跳、预算、错误、时间。
- 来源/证据：所属尝试、原始和最终 URL、来源类型、正文版本/内容摘要、抓取状态、日期出处、片段偏移和文本。
- 报告：所属尝试、结构化内容、渲染 Markdown、版本、质量检查结果；已完成历史不可被重试覆盖。
- 事件/调用：关联 task_id、attempt_id、node、call_id；记录真实或估算用量及未知消耗，不记录密钥。
- 需求、问题、结论及支持边先存入版本化 JSON；只有明确查询需求再拆表。主外键、唯一性和常用索引明确落库。
- MySQL 保留业务真相；Redis/Celery backend 不另建一套可冲突的状态来源。

### 4.3 API 初版

| 接口 | 行为 |
|---|---|
| `POST /api/v1/tasks` | 校验、幂等提交、落库，快速返回 202 与 task_id |
| `GET /api/v1/tasks` | 游标分页、状态/时间筛选 |
| `GET /api/v1/tasks/{id}` | 当前任务与尝试摘要 |
| `GET /api/v1/tasks/{id}/attempts` | 历次执行，明确当前与历史 |
| `GET /api/v1/attempts/{id}/events` | 按事件游标增量读取进度 |
| `GET /api/v1/attempts/{id}/report` | 报告结构与 Markdown 导出 |
| `GET /api/v1/attempts/{id}/evidence` | 分页证据及原文定位 |
| `POST /api/v1/tasks/{id}/cancel` | 幂等请求取消当前有效尝试 |
| `POST /api/v1/tasks/{id}/retry` | 仅允许符合条件的终态，新建尝试 |
| `/health/live`、`/health/ready` | 进程存活与关键依赖可用性，返回脱敏结果 |

相同幂等键和相同请求返回原任务；相同键但不同请求返回冲突。非法状态转换返回明确错误。列表、正文大小和事件读取均有上限。

- [x] 实现第 4.3 节接口、分页、错误响应、幂等键及非法状态转换检查。
- [x] 一次研究尝试对应一个 Celery 任务；消息只传 attempt_id 等标识，配置和业务事实从 MySQL 获取。
- [x] 提交先落库 `pending_dispatch` 再发布；发布成功后条件更新 queued，不能覆盖已被 Worker 推进的 running 状态。
- [x] 单一周期调度入口扫描未派发及过久未开始的尝试，按次数和期限有限补发；用 MySQL 条件更新保护竞争，重复消息允许到达但不能重复取得有效执行权。
- [x] Worker 以原子条件更新领取尝试，生成执行令牌；重复消息/终态消息直接结束，写入与最终提交检查令牌和取消状态。
- [x] 运行心跳与业务阶段进度分开；过期执行标记异常并失效旧令牌，旧 Worker 的迟到结果不能覆盖新尝试。首版优先显式重试，不自动无限重跑整个研究。
- [x] 上游超时、429、部分 5xx 等按分类有限重试，鉴权/请求错误不盲目重试；HTTP、图内与队列层不得形成乘法式重试。
- [x] 记录失败请求的未知用量和重试累计成本；每尝试有硬预算，任务级总预算覆盖多次重试，不能靠新建尝试绕过上限。
- [x] queued 取消使后续消息失效；running 在节点/外部调用边界检查取消并使用短超时收敛，不宣称立即终止已经发出的外部请求。
- [x] UI 断开后任务继续；Worker 中断后任务不永久 running，用户能看见失败原因并创建新尝试。

必须如实记录的边界：目标是幂等业务提交和有界重复执行，不是外部模型调用 exactly-once。Worker 与网络故障可能造成已发生但未记账的调用；不得隐藏这一成本风险。

验收：用真实 MySQL、Redis、Worker 进程验证重复投递、派发中断、Redis 暂时不可用、Worker 终止、取消竞争、迟到写入、终态保存失败；不只依靠 eager 模式测试。

## 6. 必须通过的验收矩阵

| 领域 | 最低验收场景 | 证据 |

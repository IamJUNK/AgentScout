## 发现与处理

1. 首次证据评估和写作返回 `finish_reason=length`，系统输出明确标注未完成的资料摘录。DeepSeek 官方说明 Flash 默认开启思考模式；新增 `LLM_THINKING_MODE` 配置，本地设置 `disabled`，默认兼容行为仍不发送扩展字段。第二次完整生成模型报告，但不能将这一观察归纳为普遍的性能或质量提升。
2. 引用检查曾把资料摘录中的转义 Markdown 链接当成非法报告引用。已修正，并增加回归测试；转义的证据链接也不能绕过引用检查。解析器仍是有限的规则解析。
3. 第二次报告给出了“只能有一个写入者”和“仍可能发生 SQLITE_BUSY”两项结论，实际下载的 SQLite 官方正文中能找到对应原句。但报告中的部分官方页面引用使用的是搜索摘要证据，不能将这些引用都称为正文引用；另外包含已披露的论坛二手引文。模型语义检查判通过，但结构检查只有 5/16 正文单位有本段引用，因此标为 `needs_review`。该比例不是逐句准确率。结论、引用原文和限制说明分段时，模型仍可能漏引；已明确写作提示，没有放宽门槛。
4. 第二次抓取到 31,487 字符的官方正文，入选片段中包含正文后部内容。这验证了这次任务能使用超过原 8,000 字符范围的内容，但有限证据预算仍会舍弃片段，不代表全文无遗漏。
5. 第三次出现远端连接中断，触发一次有限重试和证据评估降级。报告修复又被预算检查拒绝，保留原报告。实际返回 Token 未包含失败请求的未知消耗；预算会预留该请求的用量，因此 13,603 个已知 Token 不等于全部预算消耗。
6. 第三次实际读到的来源全是用户论坛，未取得要求的官方文档正文；问题评估与报告审查指出来源缺口，最终为 `partial`。官方域名下的论坛不能自动视为官方文档。来源优先级、同页不同 URL 的重复候选及引用格式稳定性仍需改善；本次尚未完成通用的来源权威性排序。
7. 本地真实凭据会影响界面的默认运行模式；已隔离 UI 自动测试设置，防止自动化测试误用真实服务。

## 范围与复现

每次上限：2 个问题、4 次搜索、4 个页面、2 轮、10 次模型调用、30,000 Token；证据预算 2,500、上下文预算 12,000；规划/写作/审查输出预算分别 1,200/2,000/1,800；模型超时 45 秒，协作式研究预算 180 秒。仅为本次低成本冒烟参数，不是默认生产预算。`force_refresh=True`，搜索每次取 3 个候选。

实际模型 usage 合计 53,978 Token。没有配置单价，也未核对供应商账单，金额未知；系统估算为零不能解释为免费。日志、状态与报告不包含凭据，SQLite 数据库被 Git 忽略。

本地复现：配置 `.env` 后，在项目目录执行 `python scripts/run_live_smoke.py sqlite-wal-attributed`。当前脚本会覆盖该标签的输出，新实验应先留存旧结果或使用新的输出标签。

离线自动化检查：`python -m pytest -q`，85 项通过。其作用是验证规定行为与异常处理，不能替代真实模型质量评估。最新写作提示中新增的原文链接转义要求尚未再次联网验证。

依据：[DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode)。每次原始结果保存在对应的 `*-state.json`、`*-summary.json` 和 `*-report.md` 中；首次汇总为 `summary.json`。
